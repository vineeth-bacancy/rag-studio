## 4. Architecture (decide once, use everywhere)

### 4.1 One retrieval pipeline for Ask, Evaluation and How it works

Today `eval._one` searches, then `answer.ask` searches again, and the run flags
"The answer used different passages" when they differ. LLM rewriting would break
that and double the Colab work.

- **Keep `Retriever.search` as the first-stage primitive.** Add
  **`retrieve.run(question, *, retriever, k, spec, history=None,
  remote_client=None, reranker=None) -> Iterator[event]`**, which yields
  `("stage", Step)` and ends with `("found", Found)`.
  - The stages are `rewrite`, `search` (one per query), `fuse`, `rerank` and
    `round n`.
  - `Found` holds:
    - `hits`: the deep list, up to 50;
    - `lists`, `rewrites` and `rounds`;
    - `timings` and `network`;
    - `standalone_question`;
    - `cache`: hit or miss per remote output.
  - The plain dense, bm25 and hybrid paths stay **byte-identical**.
  - Import `rewrite` and `agent` lazily: `agent` needs `retrieve`.
- **Fixed order of operations, recorded in `describe()`:** rewrite → search
  each query → fuse (RRF K=60) → limit per section → rerank the top 20 →
  cut to k.
- **`answer.ask(..., found=None, chat_id=None, as_typed=False)`**
  - It runs `retrieve.run` itself unless `found` is given.
  - It re-yields the stages so SSE shows them live.
  - New stages appear **only when their switch is on**, so the stage-order
    asserts in `tests/test_ask.py:22-24` still hold.
  - `_source` (`answer.py:83-92`) adds `context` so Ask can show "Context line
    (written by …)".
- **Evaluation runs in two passes** (memory, and one retrieval per question).
  1. For every question, `retrieve.run` gives `hit_rank` from `hits[:k]`,
     `best_rank` from the deep list, and stores `rewrites`, `rounds` and rerank
     movement per question.
  2. **Unload the reranker and EmbeddingGemma 2**: add `STModel.release()` plus
     `gc` and `malloc_trim`.
  3. Then `ask(found=...)` per question.
  - Put a lock around reranker inference, because an Ask can run during an
    app-started evaluation.
- **`SearchSpec`** gains optional fields:
  - `rerank: str | None`, an id in `rerank.RERANKERS`;
  - `rerank_depth: int = 20`;
  - `rewrite: str | None`: `decompose`, `multi` or `hyde`;
  - `agent_rounds: int | None`.
  - `describe()` adds each one only when it is set.
  - `eval._config` records each component's **stable** `describe()` under
    `retrieval.rerank`, `retrieval.rewrite` and `retrieval.agent`: model,
    digest or HF revision, dtype, where it runs, prompt version and sha, depth,
    and `num_ctx`.
  - **Volatile measurements** (memory, network, GPU name, load times) go to
    `config.runtime` or the per-question results, **never** `retrieval`.
- **Run grouping (`eval.py:438-490, 616`).** `config_key`, `variant_key` and
  `_brief` key on the canonical JSON of `retrieval`, minus `word_index`.
  - It was checked that this groups all 78 existing runs exactly as today.
  - Add a test: keep the old key as `_legacy_key`, and assert that new-key
    equality ⇔ old-key equality over fixtures for dense, bm25 on
    `text`/`search_text`, hybrid, and cap.
- **Run records.**
  - `_upgrade_row` (`eval.py:604`) defaults `rewrites`, `rounds` and `network`.
  - **MRR and recall@20** are computed from `results[].best_rank` in
    `summarize`/`_variant`, so old runs show them too.
  - Also report single-hop vs multi-hop splits and tokens sent to the answer
    model (research §10, `research.md:370-375`).

### 4.3 Network: compression and no waiting on the tunnel (user requirement)

1. **One kept-alive `httpx.Client` per `(url, token)`**, cached in `remote.py`
   and closed on connect and disconnect.
   - Today `llm.py:107-128,209` use module-level `httpx.get`/`post`/`stream`,
     and `remote.client()` builds a new client each call, so every request opens
     a new TLS connection through the tunnel.
   - Prove reuse: count connections over 20 calls, and time the first call
     against the rest.
   - Try `http2=True` only if the numbers show it helps (it needs `h2`).
2. **Gzip requests.**
   - httpx never compresses requests, so do it by hand: for bodies of 4 KB or
     more, send `content=gzip.compress(json_bytes)` with
     `Content-Encoding: gzip`.
   - The gateway inflates with a streaming `zlib.decompressobj` under a hard cap
     (inflated ≤ `MAX_BODY_BYTES`, so a bomb gets 413). Corrupt gzip gets 400,
     an unknown encoding 415. It forwards plain JSON upstream.
3. **Gzip responses.**
   - The gateway already gzips replies of 16 KB or more. **Measure it on a real
     runtime first**; this is an open M4 item. Record raw against wire bytes
     (`Response.num_bytes_downloaded`) and the time for an 8B embed batch.
   - Try a 4 KB threshold.
4. **Batch on the runtime.** Context lines go through `/context` batches, with
   the window sent once and the runtime looping over loopback. Reranking is one
   request per question with every candidate.
5. **Pipeline.**
   - Keep 2 batches in flight in bulk jobs, so the GPU never idles while the
     tunnel carries the next request.
   - While a remote multi-query or HyDE rewrite is in flight, search the
     original question locally; it is fused in anyway.
6. **Timeouts.**
   - The remote read timeout becomes about 95 s (`llm.py:33` is 300 s).
   - **Map HTTP 524** to "The request took longer than the tunnel's 100 s
     limit. Send a smaller batch." Today it reads "the runtime has probably
     stopped" (`llm.py:101-103`).
7. **Measure and show.**
   - Every remote call records `bytes_out`/`bytes_in` (raw and wire),
     `wall_ms`, and `server_ms` (worker `compute_ms`, Ollama `total_duration`,
     or `Server-Timing`).
   - The trace shows "Network 0.4 s · Remote AI 1.2 s".
   - Runs keep these numbers under `runtime`/results, and
     `docs/02-remote-gpu.md` gets a before/after table.

### 4.4 Contextual retrieval

- **Profiles.**
  - `{pymupdf,docling}-structure-embeddinggemma2-ctx`, with `contextual=True`.
  - `config()` adds `context: {model, prompt_version, prompt_sha256,
    window_policy}` **only for these profiles**, and drops the key when it is
    None.
  - The runtime `qwen3:8b` digest and the generation order go in
    `manifest["context"]`, because `config()` is static and is compared on every
    open (`retrieve.py:129`).
- **Windows** (`context.py`).
  - Split each contiguous same-section run of passages, in document order and by
    `meta.section_path`, into **fixed blocks of ≤ 6,000 tokens**. Every passage
    in a block shares that block's window: the document title, a short outline
    of headings, and the block text.
  - Shared windows are what let Ollama reuse the prefix. Centred per-passage
    windows would share nothing.
  - **Don't edit `structure.py`**: that changes the cleaned-document cache key
    (`ingest.py:61`).
- **Prompt.** `context-v1` (sha recorded) is Anthropic's wording adapted to 1-2
  sentences. The window is fenced as data, the window comes first and the
  passage last.
- **Cache.** `data/cache/context/<model-digest>/<prompt-sha>/<key>.json`.
  - `key = sha256(window_policy + window text + label\ntext)`, using the
    **context-free** text, so the key never depends on its own output.
  - Writes are atomic, and the cache is resumable.
  - **Back it up**: export to `data/context/<profile>.jsonl`, and ask the user
    at close-out whether to commit it. The lines cost hours of T4 time and can't
    be reproduced byte for byte.
- **The job.**
  - Use a separate `.context.lock` and `jobs/<profile>.context.json` with
    `on: "colab"`. **Not** the build lock or the build job file: those would
    show up as an "index build" and block or confuse evaluations
    (`ingest.py:203-217`, `eval.py:316-319`).
  - It has its own stage for cancel polling.
  - Extract `_build`'s parse → clean → chunk half (`ingest.py:364-398`) into a
    shared `passages_for(profile)`, so the job and the build cut identical
    passages.
  - Send passages in block order, keep 2 batches in flight, and **measure the

  - **Check determinism**: regenerate 20 lines in a shuffled order and report
    the exact-match rate.

### 4.5 Query rewriting, chat memory, the agentic loop

- **Remote LLM output cache.**
  - Rewrites, standalone questions and controller decisions are cached, keyed by
    (model digest, prompt sha, `num_ctx`, input), like the context cache.
  - Each question records a hit or a miss.
  - This makes a retrieval-only run and its scorecard run see the **same**
    rewrites.
- **`rewrite.py`**: each technique has a versioned prompt with JSON-schema
  output, run by the `rewrite` role.
  - **`decompose`**: 1-3 sub-questions, each searched, then pooled and
    deduplicated. With a reranker on, the pool is reranked against the original
    question; otherwise it is round-robin filled to k.
  - **`multi`**: 3 phrasings plus the original, fused with RRF.
  - **`hyde`**: a hypothetical passage of ≤ 120 words, **embedded with the
    profile's document format**. That is the same model, so rule 3 holds;
    record `embed_as: "document"`. It is fused by RRF with the original query.
  - **`standalone(question, history)`**: turns a follow-up into a standalone
    question.
  - Junk output is an error, never a silent pass-through.
- **`chat.py`**: conversations in `data/chat/<id>.json`.
  - `id` must match `^[0-9a-f]{32}$`, so no path traversal, and every write is
    atomic.
  - **Turns** record the question, the standalone question, the answer, the
    citation map, the sources (chunk id, doc, page), the setup, refused, and a
    trace summary.
  - **Memory acts only through the rewrite.** The answer model sees the
    standalone question plus passages under the same prompt v3, so answers stay
    comparable with the scorecard.
  - **Remote AI down.** A follow-up gets an `error`: "Follow-up questions are
    rewritten by Remote AI, which is not connected. Connect it in Settings, or
    ask the question in full." "Ask as typed" re-sends it with `as_typed`,
    recorded as `rewritten: false`.
  - Logs hold counts only.
- **`agent.py`**: the controller is the `rewrite` role.
  - **Spec.** `AgentSpec(rounds=3, budget_s=90, budget_tokens=…)`, prompt
    `agent-v1`, and a JSON schema `{action: search|answer, query ≤300 chars,
    doc: enum(known doc_ids)|null, reason ≤200}`.
  - **Rounds.** Round 1 is always the normal pipeline search. After that the
    controller sees fenced evidence (id, doc, page, label, first 300 chars) and
    chooses.
  - **The doc filter is a validated doc_id** passed as a LanceDB prefilter. Add
    `where` support to `store.search_dense` and `search_bm25`
    (`store.py:185-214`), and check that FTS supports a prefilter. **Free text
    never reaches a `where` string.**
  - **Stop reasons**: enough evidence, rounds, time, tokens, a repeated query,
    bad output. Record the reason and the tokens per round.
  - **Answering.** The pool is reranked against the original question (when a
    reranker is on), cut to the top 5, and answered by the local answer model.
    Each round is an SSE `stage` and a trace step.
- **CLI and API switches.**
  - `./rag eval` gains `--rerank`, `--rewrite` and `--agent ROUNDS`.
  - `AskRequest` and `RunRequest` (`main.py:351,437`) and `/api/learn/search`
    gain validated fields, plus `chat_id` and `as_typed`.
  - Chat routes: `GET /api/chats`, `GET` and `DELETE /api/chats/{id}`.
  - `./rag eval` with no `--set` (`cli.py:120`) **excludes remote-only sets**
    (Set E).

## 8. Ladder protocol and run budget

1. **Retrieval-only first:** `./rag eval --mode retrieval --set a b d [e]`.
   - It is deterministic for dense, BM25 and hybrid.
   - For the LLM switches it is repeatable only through the remote output cache
     (§4.5).
   - With the CPU reranker, expect 20-35 s per question.
2. **Then the scorecard:** `./rag eval --set a b d --profile <p> --prompt v3
   <switches> --ladder N --label "<…>"`. Run them in sequence, in the
   background.
   - Expect about 14-16 scorecards at 10-25 min each.
   - Rows: 6a-6f, 7a/b, 8a-f and 9a/b, plus a retrieval-only reranker check on
     the baseline (B4 at rank 11 → ?) for the docs and step 4.
3. **Write each row into `docs/ladder.md` in the row-5 format:**
   - a one-change paragraph;
   - a variant table with the run ids, A+D, recall A/B/D, run time, **MRR,
     recall@20, s/question, network against Remote AI time**;
   - "What row N says.";
   - the defaults.
4. **Read the numbers carefully.** It is one run each over 25 questions, so a
   difference of 2 is a hint, not proof.
